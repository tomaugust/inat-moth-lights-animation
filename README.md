# iNaturalist Moth Lights

**Live site: https://tomaugust.github.io/inat-moth-lights-animation/**

This project will turn recently uploaded moth observations from around the world on iNaturalist into a continuous, living animation around a glowing moth light. New observations will enter a calm, bounded stream with species details, photographs and attribution, while making clear that the display represents recently shared records rather than real-time moth abundance or movement.

The project builds on the visual design and animation engine developed in [tomaugust/moth-lights-animation](https://github.com/tomaugust/moth-lights-animation). See that original repository for details of how the canvas animation, moth movement, interactions and audio work. The completed initial API research, timing model, decisions and reproducible spike are documented in [research/phase-0.md](research/phase-0.md).

## Project structure

Phase 1 extracted the previous single-file, PowerShell-generated `index.html` into plain ES modules so the live site can be developed as normal source files:

- `index.html` — thin HTML shell that loads `styles/main.css` and `src/app.js`.
- `styles/main.css` — all animation, layout and control styling.
- `src/config-store.js` — the shared, live-updating config binding.
- `src/animation-engine.js` — moth physics, orbit math and canvas drawing (stateless, pure functions).
- `src/audio-engine.js` — chime and drone synthesis.
- `src/app.js` — DOM wiring, canvas controller, launch screen, and the bootstrap that fetches `config/site-config.json` and starts the animation.
- `config/site-config.json` — the real animation/species/moth data currently shown on the site.

**Update:** `index.html`/`src/app.js` no longer runs the static, fixed-timeline animation described below — see "Phase 5: production goes live" further down. The rest of this section (Phases 2-4) still accurately describes the components that live wiring is built from.

Phase 2 added the live-data engine components, proven against the recorded fixtures from Phase 0 rather than a real API call:

- `src/observation-adapter.js` — validates and normalizes a raw observation payload (the contract in `fixtures/observations-*.json`) into records the rest of the app can trust; a missing id or unparseable date drops just that record instead of breaking the batch.
- `src/species-style.js` — deterministic per-taxon visual/audio styling (color, chime notes, size, speed, drift) hashed from the taxon ID, so a global stream never needs a hand-maintained species list. Anything not identified to species level gets one shared grey "unknown" profile.
- `src/observation-queue.js` — dedupes by observation id, paces release by the source `createdAt` gaps (scaled, jittered, clamped), caps how many overdue observations catch up in one call, keeps the oldest observations on overflow, and persists its cursor/seen-id window (tolerating missing or corrupt storage).
- `src/moth-store.js` — the mutable replacement for the old fixed `config.moths` timeline: each observation gets an independent entry/orbit/exit lifecycle from a monotonic clock, bounded to `maxActiveMoths`, with a focused (hovered/tapped) moth kept alive past its exit until focus clears or a grace period elapses. Its output is drop-in compatible with `animation-engine.js`'s `projectMoth`/`drawScene` — no rendering code changed.
- `fixtures-demo.html` / `src/fixtures-demo.js` — a minimal page (no launch screen, audio or side panel — that polish is Phase 5) wiring all of the above together: it polls the three committed fixture files on a loop, replaying them with relabeled ids/timestamps after the first pass so the queue and store are exercised continuously rather than draining once, and shows a live active/pending count for an easy soak check.

Phase 3 added a real (development-only) API poller, reusing the same queue/store/adapter from Phase 2 unchanged:

- `src/inaturalist-client.js` — polls the real `https://api.inaturalist.org/v2/observations` directly from the browser (the Phase 0 spike confirmed CORS allows this for a prototype), maps each raw v2 result into the same contract shape `observation-adapter.js` already validates, advances the `id_above` cursor so pages aren't replayed, and never overlaps polls. It tracks the `starting` / `live` / `quiet` / `stale` / `offline` / `rate-limited` / `fatal-schema-error` connection states from inat_website.txt section 7, honors `Retry-After` on a 429, backs off with jitter on other failures (resetting after a success), and stops polling on `offline`/resumes immediately on `online`. A browser `fetch()` cannot set a custom `User-Agent` header, so the "descriptive User-Agent" requirement from section 5.2 genuinely can't be met until Phase 4's server-side adapter exists — this file documents that rather than pretending otherwise.
- `live-demo.html` / `src/live-demo.js` — wires the client into the Phase 2 queue/store/renderer and shows connection state, request count and an observed observations/minute rate next to the Phase 0 measurement (~25-41/min) for comparison. Before starting the poll it also resolves the visitor's own country via `src/geolocation.js` (browser Geolocation API → iNaturalist `GET /v1/places/nearby`, resolving the coordinates to a country-level `place_id`) and shows the resolved (or, on any failure, the United Kingdom default) country as the first line of the status readout, e.g. `location: United Kingdom (from your browser's location)`. **This page is deliberately not deployed** (see `.github/workflows/pages.yml`) — it makes real requests to a third party, and Phase 3 is explicitly a local dev prototype, not the production architecture.
- `src/geolocation.js` — `resolveUserPlace()` wraps `navigator.geolocation.getCurrentPosition`, resolves the coordinates to a country place via `places/nearby`, and always resolves (never rejects) to `{ placeId, countryName, source }` — `source` is `"geolocation"` on success, or `"unsupported"` / `"denied"` / `"unavailable"` / `"lookup-failed"` when it falls back to `DEFAULT_PLACE_ID` (United Kingdom, exported from `src/inaturalist-client.js`).

**Update (Phase 14): the Worker described in this section was later removed** — the site now calls `api.inaturalist.org` directly (see Phase 14 further down). This section is kept as an accurate record of how Phases 4-13 worked, not a description of the current architecture.

Phase 4 adds the shared cache/API adapter — a Cloudflare Worker sitting between every visitor's browser and iNaturalist:

- `worker/src/index.js` — validates and normalizes upstream responses (reusing `mapRawObservationToContract`/`fetchAllObservationsInWindow` from `src/inaturalist-client.js` and `parseObservationsResponse` from `src/observation-adapter.js` unchanged, so the contract can't drift between the direct-client and adapter paths), sets a real `User-Agent` (something only a server-side fetch can do — a browser silently strips a custom one), and restricts CORS to an allow-listed origin list. Rather than caching per client cursor, it always asks upstream for *every* observation in the configured taxon/place/24h window — `fetchAllObservationsInWindow` pages through as many requests as that takes (ascending by id, capped at `MAX_WINDOW_PAGES`, paced `PAGE_DELAY_MS` apart), not just the newest `per_page` — and caches that combined response in Workers KV, keyed by `PLACE_ID` (`observations:{placeId}`), for a shared TTL (default 1800s/30min) — so any number of concurrent browsers anywhere cost exactly one refresh; each client's own `ObservationQueue` already dedupes by id, so handing everyone "everything currently in the window" is exactly what a shared feed should do. **The cache is Workers KV, not `caches.default`, deliberately**: `caches.default` is per-Cloudflare-colo, and a real production incident showed why that's a real problem, not a theoretical one — a UK colo's own refresh hit iNaturalist's rate limit, that colo's stale-backup entry had also expired, and every visitor routed there got a hard 502 for as long as that colo's own attempts kept failing, while every other colo (and every check made from outside the UK) looked completely healthy. KV is globally replicated: one successful refresh from any colo populates a value every colo reads, so no single unlucky colo can strand its own visitors — the tradeoff is KV's own eventual-consistency propagation (up to ~60s), which only ever means "briefly serves the previous still-valid entry", never "serves nothing". 1800s plus the 1s inter-page pacing were chosen after a separate, earlier rate-limiting incident (real window volume, ~4-10 pages/745-2,000 records, was regularly firing every page back to back with no delay) to keep worldwide upstream request volume comfortably under iNaturalist's ~1 req/s recommended ceiling — now a real global ceiling, not a per-colo hope. `MAX_WINDOW_PAGES` is deliberately set to 5 (1,000 records) — *below* that measured real volume, as a hard safety valve on burst size rather than a "stay above real volume" ceiling: on a busier-than-1,000-records window it truncates and silently misses whatever falls past page 5, an accepted trade for a tighter worst-case request burst. Every query is also hard-bounded to the last 24 hours (`created_d1`, see `DEFAULT_LOOKBACK_HOURS` in `src/inaturalist-client.js`) — never temporally unbounded. On a timeout, 429, or non-2xx from any page it discards that refresh entirely and falls back to a separate, much-longer-lived "last known good" cached copy marked `stale: true` — never an empty/fabricated or partial-window list — so a real outage degrades gracefully instead of breaking every viewer at once.
- `worker/wrangler.toml` — Cloudflare Worker config: a `[[kv_namespaces]]` binding (`OBSERVATIONS_KV`) for the shared cache above, plus `[vars]` for allow-listed CORS origins, taxon scope, place scope (`PLACE_ID`, default `6857` = United Kingdom — an iNaturalist `place_id`, not a lat/lng bounding box), page size, cache TTL, inter-page pacing (`PAGE_DELAY_MS`), upstream timeout — all tunable per-deployment. The KV binding's `id` is a placeholder (`__OBSERVATIONS_KV_ID__`); see the deploy instructions below for how it gets filled in.
- `src/inaturalist-client.js` gained a `buildUrl`/`upstreamShape: "adapter-contract"` option so the exact same `InatClient` (state machine, backoff, overlap prevention — all unchanged) can point at a deployed adapter instead of iNaturalist directly, treating the response as the already-normalized contract instead of a raw v2 page.

**Deployed** at `https://inat-moth-lights-adapter.tomaugust1985.workers.dev` (see `.github/workflows/deploy-worker.yml`, which redeploys on every push to `main` touching `worker/**` or the shared client/adapter modules). `ALLOWED_ORIGINS` in `wrangler.toml` includes the site's real GitHub Pages origin (`https://tomaugust.github.io`) and `http://localhost:8080` for local dev.

## Phase 5: production goes live

`index.html`/`src/app.js` now runs the live pipeline instead of the old static, fixed-timeline animation: `InatClient` (in `upstreamShape: "adapter-contract"` mode, pointed at the deployed Worker above) feeds `ObservationQueue` feeds `MothStore`, driven by a real monotonic clock (`performance.now()/1000`) instead of the old looping `animationTime` — the same components Phase 2/3 already proved, just wired into the production page instead of the dev-only `live-demo.html`.

What changed to make that work:
- **The timeline scrubber is gone** — a live feed has no fixed length to scrub into. The active-moths side panel, hover popout, sound toggle and launch screen are unchanged.
- **Hovering/focusing a moth (canvas or side-panel card) freezes the whole scene** at the instant focus began, resuming exactly where it left off once focus clears — matching the original demo's hover behavior. Implemented as a held render clock (`app.js`'s `currentSceneSeconds()`/`currentRenderTimestamp()`, set once when `hoverState.hoveredMothId` becomes non-null and cleared when it's next `null`) that every reader of "now" shares — rendering, canvas hit-testing, and the side-panel list all agree on the same frozen instant, so nothing visibly drifts out of sync with what's on screen. Only rendering and moth admission/expiry pause; the real network poll and `ObservationQueue` keep running underneath, so whatever arrived during the freeze is simply admitted the moment focus clears, with no backlog lost. (An earlier version of this live rewrite used `MothStore.focusMoth()`'s grace-period mechanism instead — extending just the hovered moth's own lifetime while everything else kept moving — but that read as the animation merely slowing down rather than pausing, so it was reverted.)
- **`src/audio-engine.js`** no longer cross-references a fixed `config.species` list (live taxa are unbounded); it now triggers chimes directly from whichever moths are actually active, using each one's own `chimeNote`/`chimeNotes` (already assigned deterministically per taxon by `species-style.js`).
- **The active-moths card and canvas hover popout show the observation's real observed time** (`moth.observedAtMs`, carried through by `moth-store.js`) instead of a fictional entry/exit range on a clock that no longer exists.
- **Real network polling starts as soon as the scene is constructed**, including during the brief light-only preview before the launch screen finishes fading, so there's already a backlog of real observations ready to render the instant the reveal completes.
- **UK-only at first** — the Worker's cache was hard-set to one `PLACE_ID` and didn't read anything from the client's request. Superseded by Phase 7 below (per-visitor country), which wires up `src/geolocation.js` — built during this phase but not connected to `app.js` until then.
- **`config/site-config.json`'s `species`/`moths` arrays are no longer read by `app.js`** (real per-taxon styling comes from `species-style.js`'s deterministic hash, not a curated list) but haven't been deleted from the file — left as a deliberate, separate cleanup decision rather than bundled into this change.
- **The production `ObservationQueue` no longer persists to `localStorage`** (unlike `live-demo.js`'s and `fixtures-demo.js`'s, which still do). The Worker adapter is stateless and returns the *entire* current 24h window on every poll, not an incremental delta — persisting the seen-ID dedup across page loads meant a real visitor reloading, or simply revisiting later the same day, got zero new observations on the second load: every ID in the (mostly still-overlapping) rolling window had already been marked "seen" on the first. This was a real production bug (moths would render on a first-ever visit to this storage key, then never again on any later visit in the same browser) found via a real bug report and reproduced directly against a captured live payload before being fixed. In-memory dedup (which does persist for the page's own lifetime, so a poll doesn't re-enqueue the same batch every 30s) already covers what the module's persistence was actually needed for elsewhere; a fresh load of the live page is meant to replay the current window from scratch anyway.
- **A small always-on `#debug-status` readout** (connection state, request/observation counts, queue/store sizes) was added next to the loading indicator so a real-device bug report can include exact diagnostic state without needing devtools access on a phone.
- **`InatClient`'s fetch timeout is raised to 45s for this adapter** (`requestTimeoutSeconds` in `app.js`'s client construction) — its own 15s default was too tight once the Worker started pacing multi-page refreshes (see `PAGE_DELAY_MS` above): a cold-cache refresh measured ~7-8s from a fast connection alone, and a real mobile connection transferring the ~300-400KB response could push past 15s, aborting the fetch and leaving the scene empty until the next ~60s-backed-off retry. Found via the `#debug-status` readout showing `state=stale reqs=1 obs=0` on a real device. **(Update, Phase 14: this override was removed along with the Worker** — a direct single-page fetch has no such multi-page latency, so `InatClient`'s ordinary 15s default applies again.)
- **`test/e2e/site.test.js` now mocks the iNaturalist photo CDN too**, not just the Worker adapter — its `liveObservation()` fixture's photo URL doesn't correspond to a real photo, which this project's own sandboxed dev environment (unable to reach any external domain) had been masking, but which a real-internet CI runner correctly surfaced as a genuine 404, failing CI on every commit since live-wiring shipped.

**Update (Phase 14): there is no longer anything to deploy here.** The Worker described above was removed in favor of calling `api.inaturalist.org` directly from the browser — see Phase 14 further down. `index.html`/`src/app.js` is the only thing GitHub Pages serves (`.github/workflows/pages.yml`); there's no separate backend, secrets, or KV namespace to provision.

### Run it locally

The app fetches its config over `fetch()`, so it needs to be served over HTTP rather than opened as a `file://` URL:

```sh
npm install
npm run serve
# then open http://localhost:8080/               (the production animation)
# or       http://localhost:8080/fixtures-demo.html (the Phase 2 fixture/queue/store demo)
# or       http://localhost:8080/live-demo.html     (the Phase 3 real-API prototype — makes real requests to iNaturalist)
```

Any static file server works equally well (`python3 -m http.server`, `npx serve`, etc.).

## Phase 6: pacing for real-world data density

A real abundant-data review (the UK regularly has 700-2,700+ observations in its 24h window) found two compounding problems, addressed together since a fix to one changes the pressure on the other:

- **Too busy, too fast.** `MothStore`'s original 50 concurrent moths at 4-10s each meant species cards flew by too fast to actually read. Lowered to `maxActiveMoths: 10` with duration doubled to `minMothDurationSeconds: 8` / `maxMothDurationSeconds: 20` (avg 7s → 14s) — a deliberate legibility choice, not a technical limit.
- **Abundant windows overwhelm the store's own throughput.** With 10 slots and a ~14s average lifetime, sustainable admission is only ~0.71/sec — comfortably showing everything in an abundant window (over 1,000 distinct observations isn't unusual) would take 20+ minutes instead of the intended ~60s cycle. `ObservationQueue` now thins an overflowing pending queue with `selectDiverseSample()` (round-robining across distinct species) instead of a plain oldest-first truncation, down to `targetSampleSize: 45` — derived from `maxActiveMoths` and the duration range above (see the comment in `observation-queue.js`; the two must be updated together). Round-robining means a common species can't crowd out everything else in the sample, the way keeping-the-oldest-N could.
- **Sparse windows have the opposite problem — not enough data exists, no pacing math fixes that.** `worker/src/index.js` now retries with a 7-day window (`SPARSE_LOOKBACK_HOURS`) whenever the default 24h window returns fewer than `SPARSE_OBSERVATION_THRESHOLD` (30) observations, using the wider result only if it actually has more. This never fires for the UK's current volume — it's there for a future lower-volume `place_id`, since per-country caching (see the KV section above) is only one piece of what multi-country support needs.
- **Hovering/focusing a moth (canvas or side-panel card) freezes the whole scene** at the instant focus began, resuming exactly where it left off once focus clears — see the Phase 5 section above for the implementation.

## Phase 7: per-visitor country

The site now resolves each visitor's own country (`src/geolocation.js`'s `resolveUserPlace()`, built in Phase 5 but not connected until now) instead of always showing the UK.

- **Starts with the UK default immediately, then switches if resolution finds somewhere else.** `app.js` calls `startClientForPlace(DEFAULT_PLACE_ID)` synchronously — the exact same instant-start behavior as before this phase — and resolves the visitor's real country in the background. If that resolves to a different `place_id`, it cuts over: `client.stop()`, a fresh `ObservationQueue`/`MothStore` (a different country is a different feed, not a continuation — the old country's moths don't linger alongside the new one's), the loading indicator reappears, and `startClientForPlace()` runs again for the new place. Resolving to the UK anyway (a real UK visitor, or any failure's fallback — `resolveUserPlace()` never rejects) means no switch and no visible change. This two-step design replaced an initial, simpler attempt that `await`ed `resolveUserPlace()` *before* starting the client at all: testing surfaced that a real, unanswered browser geolocation permission prompt doesn't error, it just hangs until `resolveUserPlace()`'s own ~8s fallback timeout — meaning blocking on it would have turned an instant start into an ~8s wait for most first-time visitors (anyone who doesn't proactively respond to the permission prompt), not a rare edge case.
- **The heading and page title update to match** (`countryHeading()`/`countryDescription()` in `app.js`) — `"{Country} Moths"` for everywhere except the UK default, which keeps the original "UK Moths" copy (`FALLBACK_COUNTRY_NAME` from `geolocation.js` is the same string either way, so a real UK visitor and any failure-fallback both read identically). The description's "across {country}" phrasing doesn't attempt correct English articles for every country name (a real edge case, e.g. "across Netherlands" rather than "across the Netherlands") — a known, accepted minor imperfection rather than a hand-maintained per-country grammar table.
- **`worker/src/index.js` accepts an optional `?place_id=` query param**, validated as a positive integer, overriding the deploy-time `PLACE_ID` env default. Every cache key was already scoped by `place_id` (Phase 6's KV work anticipated exactly this), so a new country is just a new, independently-cached-and-refreshed KV entry — no redesign. Deliberately just a sanity bound, not a curated allowlist of real iNaturalist place ids: this is a public, unauthenticated endpoint (CORS restricts which browser origins can *read* a response, not who can *request* one at all), so an allowlist would only protect against a caller who could already request any place_id directly anyway, for the cost of keeping it in sync with every country `resolveUserPlace()` might return. Revisit if real abuse shows up.
- **Fixed a real concurrency bug found while adding this**: the shared-refresh de-duplication (`inFlightRefresh`, so N concurrent callers hitting a cache miss cost one upstream fetch, not N) was a single module-level variable. With only ever one `place_id` possible, that was fine; with several now possible, a concurrent miss for one country could have incorrectly awaited (and received) a *different* country's in-flight refresh. Now a `Map` keyed by `place_id` — verified with a test that races two different countries' concurrent misses and asserts each gets its own data.
- Tested end-to-end with real browser geolocation mocking (`test/helpers/geolocation.mjs`, already used by the dev-only `live-demo.html` suite): a delayed `places/nearby` response creates a reliable window to observe the UK default before the switch, then asserts the heading and the active-moths panel both fully reflect the new country (and the old country's moth is gone, not left alongside it) — confirmed this fails without the feature (hangs waiting for a heading that never changes) and passes with it.

## Phase 8: UI/UX — loading feedback and diagnostic cleanup

- **The light itself now visibly flickers, as if the bulb hasn't warmed up yet, for as long as real data is still loading** — a deliberate visual cue in place of the scene just sitting there looking finished when it isn't. `animation-engine.js`'s `brokenLightFlicker()` combines three incommensurate-frequency waves into sharp, irregular near-blackout dips (never fully dark — there's a floor), distinct from the subtle, always-on ambient shimmer (`lightFlicker()`) used once real data has arrived. `drawScene()`/`drawLight()` take a new `isLoading` flag; `app.js`'s `isLoadingData()` derives it from the *same* signal that shows/hides the loading text (`loadingStatus`'s own `is-hidden` class) rather than a second, separately-tracked flag, so the two can never drift out of sync — including on a country switch, when the loading text reappears and the light starts sputtering again automatically. The loading text itself ("The light is still warming up — loading recent sightings…") got a matching pulse animation and a more prominent size/weight, replacing small, static, easy-to-miss copy. Verified visually (screenshotted through several frames of a deliberately delayed mocked response — confirmed the same pixel location swings from near-black to full-bright and back — then confirmed it holds steady once the delayed response resolves) and with an e2e test sampling the light's own center pixel (not the surrounding glow, which the ambient shimmer does subtly touch) across several frames, asserting a large brightness range while loading and a near-zero one once loaded.
- **The `#debug-status` diagnostic readout (added during a real production incident earlier in this project) is now hidden by default** — it was never meant for every visitor to see, and stayed visible out of expedience while chasing that incident. Opt in with `?debug` on the URL for troubleshooting a future report; without it, the element is never even populated (`app.js` only looks it up from the DOM when `?debug` is present), so it stays empty and CSS (`.debug-status:empty { display: none; }`) keeps it fully out of the way.

## Phase 9: hardening against iNaturalist rate-limiting — two layers of fallback

**Update (Phase 14): the Worker/stale-backup layer described below no longer exists, and the Colombia dataset has been replaced by a global capture** — see Phase 14.

The iNaturalist rate-limit problem (the reason for the shared Worker cache in the first place — see Phase 4) doesn't fully go away just because the cache is shared: a sustained outage or an extended rate-limit window can still outlast any single cache entry. Two independent, complementary layers now guard against that, cheaper than the self-hosting alternative (a dedicated AWS server was evaluated and shelved — see the "Alternatives considered" section below):

- **The Worker's stale-backup cache now lasts a week, not 6 hours** (`STALE_BACKUP_SECONDS` in `worker/src/index.js`). The original 6-hour window meant a bad-enough incident still ended in the empty-list 502 (`staleFallback`'s other branch) well before anyone could investigate or iNaturalist's rate limit reset. A week trades staleness (worst case, a visitor briefly sees week-old "recent" sightings) for never falling all the way back to nothing, which is the more visible and confusing failure of the two. Tested at both ends: still serves real data at 6 days 23 hours, finally falls through to the empty 502 past 7 days.
- **A small, bundled-in-the-app dataset of real observations from Colombia** (`src/fallback-observations.js`) is the last line of defense for a visitor whose very first page load can't get live data from anywhere — not the short cache, not the week-long backup either (a brand-new `place_id` with nothing cached yet, or an outage that outlasts even a week). 68 real, research-grade, individually-licensed moth observations (one per species, hand-picked from the most-favorited results of a live query against `api.inaturalist.org` scoped to moths only — see Phase 10 below — which itself turned up 34,000+ research-grade, photographed records for Colombia, confirming the "moth-rich country" premise rather than assuming it) are woven into the scene through the same `ObservationQueue`/`MothStore` pipeline live moths use, with a small banner (`#fallback-status`) explaining what's being shown and why. The moment a real batch actually arrives — even an empty (quiet) one, since that's still a working adapter — the substitute set and its banner are cleared out in favor of live data, so the two are never shown mixed together.

### Alternatives considered

- **GBIF as an iNaturalist replacement**: a real query against GBIF's API for the same UK Lepidoptera window it would need to serve found data lagging iNaturalist by 2+ weeks (GBIF ingests iNaturalist research-grade records via a periodic Darwin Core Archive sync, not a live feed) — unsuitable for a site whose whole premise is "recently shared" sightings. Ruled out.
- **Self-hosting the adapter on a dedicated AWS server** (EC2/Lightsail), so requests come from a single dedicated IP unaffected by any other iNaturalist API consumer's traffic: technically viable, but shelved for now in favor of the two cheaper layers above, which cost no new infrastructure, no domain, and none of GitHub Pages' free hosting.

## Phase 10: moths only, excluding butterflies

The site's scope had been Lepidoptera as a whole (moths and butterflies together) since Phase 0 — a later, explicit product decision narrowed it to moths only.

- **Every upstream query now sends `without_taxon_id=47224`** — 47224 is Papilionoidea, iNaturalist's own "Butterflies" superfamily (confirmed against `GET /v1/taxa?q=Papilionoidea&rank=superfamily`, whose `preferred_common_name` is literally "Butterflies"). Skippers (family Hesperiidae) are commonly thought of as their own thing, but iNaturalist's current taxonomy nests them *inside* Papilionoidea (`parent_id: 47224`, confirmed the same way) — so this single id excludes both, without a second, harder-to-maintain family allowlist to keep in sync with future taxonomic revisions.
- **`DEFAULT_WITHOUT_TAXON_ID` lives in `src/inaturalist-client.js`** (next to `taxonId`'s own default) and flows through both real query paths: `setSharedParams()` for the direct client, and the Worker's `buildUpstreamOptions()`, which reads an env override (`WITHOUT_TAXON_ID` in `worker/wrangler.toml`) the same way `TAXON_ID` already does — explicitly checked with `Number.isFinite`, not `Number(x) || DEFAULT`, so an operator can set it to `"0"` to deliberately opt back into the full order (0 would otherwise be swallowed as "unset" by `||`).
- **The Colombia fallback dataset (Phase 9) was regenerated to match** — the original 53-entry set (queried before this scope change) mixed in real butterflies. Re-querying with the same `without_taxon_id` filter turned up 34,000+ research-grade moth records for Colombia alone (versus 90,000+ for all Lepidoptera), and the curated set was rebuilt from that moths-only query so the fallback content never contradicts what the live feed itself now shows.
- **User-facing copy updated to say "moth sightings," not "moth and butterfly sightings"** (`app.js`'s `countryDescription()`, `index.html`'s initial description, and the fallback banner's "moth-rich countries" phrasing).

## Phase 11: a slower, seizure-safe loading flicker, with a 3-second minimum

A user flagged the Phase 8 loading flicker as too fast and worried about photosensitive epilepsy — a real accessibility/safety issue, not a style note.

- **Root cause: a unit bug, not just an amplitude choice.** `drawLight`/`brokenLightFlicker` (`animation-engine.js`) are called with `elapsed` in *milliseconds* (`performance.now()`), matching the neighboring ambient-shimmer function's own `config.light.flickerSpeed: 0.006` (rad/ms). The original implementation used coefficients sized as if `elapsed` were in *seconds* (e.g. `13.7`) — at `13.7` rad **per millisecond**, that's ~2,180 Hz, so far past any visible frequency that consecutive animation frames sampled essentially uncorrelated phases of it: indistinguishable from a rapid, per-frame-random strobe. This is exactly the pattern WCAG 2.3.1's general flash threshold (max 3 flashes/second) exists to rule out.
- **Fixed with real millisecond-scaled coefficients** (`0.0022`/`0.0011`/`0.0007` rad/ms — the fastest is ≈0.35 Hz, a full period taking seconds, not milliseconds), a linear (not squared) dip, and a much higher floor (0.4, not 0.06) so brightness drifts smoothly rather than slamming into near-black. Verified two ways: numerically (a standalone simulation confirmed ~0.3 dip-events/second and a worst-case ~4.3s gap between dips, both comfortably under any flash-rate concern) and visually (a screenshot sequence through a deliberately delayed load shows a slow, gentle dim-and-brighten breathing effect, not a strobe).
- **A 3-second minimum display duration** (`MIN_LOADING_DURATION_MS` in `app.js`) — the loading indicator (and its flicker) now always stays up at least this long, even when the real response arrives almost instantly (a warm cache, a fast connection), so a viewer never sees a flash of flicker lasting only a few hundred milliseconds. Implemented as a cancelable `setTimeout` scoped per client generation (`startClientForPlace`'s `hideLoadingNoSoonerThanMinimumDuration()`), correctly reset on a country switch so a pending hide from the *previous* generation can't fire early against the new one's own loading state.
- **Fixed a real edge-case bug surfaced by adding the minimum duration**: `isLoadingData()` reads live DOM state, not the frozen render clock hover/focus already holds still (`currentSceneSeconds()`/`currentRenderTimestamp()`) — so a hover-freeze that happened to straddle the loading→loaded transition could let the light's appearance visibly change while the rest of the scene stayed frozen, breaking the "nothing changes while frozen" guarantee. Fixed by capturing `frozenIsLoading` at the same instant focus begins, alongside the existing frozen timestamp/seconds, and reading it through a new `currentIsLoading()` (mirroring the existing `currentSceneSeconds()`/`currentRenderTimestamp()` pattern) everywhere `drawScene` is called.
- **Rewrote the e2e flicker test**, which had been (unknowingly) relying on the old bug's own aliasing to pass reliably at short sampling windows — real fixed-frequency slow flicker needs a longer window to reliably catch a dip regardless of phase. Now samples both a short (50ms-apart) window asserting no large frame-to-frame jump (the actual safety property) and a longer (6s) window asserting the light still visibly varies — 6s comfortably exceeds the waveform's own measured worst-case gap between dips.

### Follow-up: the flicker could go briefly invisible, or seem to appear only after loading

A user reported the fix above regressed further — flicker "stopped working" during loading, then seemed to flicker *more* right after loading finished. Investigation found no stuck-state bug (a fresh measurement confirmed the light holds perfectly steady once loading genuinely ends); the real cause was in the waveform shape itself.

- **The dip-based formula (`Math.max(0, -noise)`) clamped out the wave's entire positive half**, leaving brightness sitting perfectly flat at 1.0 for up to two full real seconds at a stretch (confirmed by measurement) — most of the time, in other words. With only a 3-second minimum display duration and a real per-visit starting phase effectively random (it's keyed to `performance.now()`, not a fixed zero), a fast/warm-cache visit could easily spend its *entire* loading window inside one of these flat stretches: no visible flicker at all, matching "stopped working." If the real network response then took a little longer than 3 seconds (very plausible on a cold cache), the dip could land squarely inside that extra time — still technically "loading," but easy to misread as flickering "after" loading, since by then the flat stretch had already made the viewer assume nothing more was coming.
- **Fixed by mapping the same three incommensurate-frequency waves directly to brightness** (`0.7 + noise * 0.3`, no clamping) instead of clamping out half the cycle into a dip — every point in the cycle is now in continuous, gentle motion, at the same safe, slow frequencies as before (unchanged: `0.0022`/`0.0011`/`0.0007` rad/ms, still ≈0.35 Hz fastest). There is no longer any stretch, at any point in the cycle, where the light sits still — verified both numerically (0ms longest near-extreme stretch, vs. 2000ms before) and with real-browser measurements across the actual 3-second minimum-duration window on a fast/warm-cache response (previously a coin flip depending on phase, now reliably shows a full, continuous dim-and-brighten sweep every time).

## Phase 12: the frozen scene resumed by jumping forward, not continuing smoothly

A user reported that hovering a moth (canvas or side-panel card) correctly froze the scene, but un-hovering made it visibly jump forward rather than resume from the same point — as if the hover had been skipped over rather than paused through.

- **Root cause: `performance.now()`/`nowSeconds()` never actually stop.** "Frozen" only ever meant *"currentSceneSeconds()/currentRenderTimestamp() keep returning one constant value while hovered"* — the underlying real clock kept running the whole time. The instant a freeze ended, those functions went straight back to reading the live (un-adjusted) clock, which had of course kept advancing — so every active moth's position/age (all computed from `currentSceneSeconds()` minus its own `entryTime`) suddenly leapt forward by however long the hover had lasted, instead of continuing smoothly from where it visibly stopped.
- **Fixed with a running freeze offset.** `app.js` now tracks `freezeOffsetSeconds`/`freezeOffsetMs`, incremented by each freeze's own real duration the moment it ends (`freezeBeganAtRealSeconds`/`Ms` mark when the *current* freeze, if any, started, purely to measure that duration). `currentSceneSeconds()`/`currentRenderTimestamp()` now subtract this running offset from the live clock whenever nothing is frozen, so time resumes exactly from the value that was being held, rather than snapping to wherever the un-adjusted clock had since reached.
- **Tested with a calibrated pixel-fingerprint comparison** (`test/e2e/site.test.js`), since a single moth's own randomized speed/radius makes an absolute pixel-diff threshold unreliable: several moths orbit concurrently for a stronger signal, and the test measures its own baselines from the same page load — ordinary short- vs. long-interval motion, and the hover UI's own visual cost (the focus popout and dimmed/focused style swap, which changes regardless of any time-jump and would otherwise contaminate a direct before/after comparison) — rather than assuming a fixed pixel-diff number. Confirmed failing against the pre-fix clock and passing against the fix.

## Phase 13: the loading flicker undershot — too slow and shallow

Immediately after Phase 11/the follow-up fix above, a user reported the opposite problem: the flicker was now so slow and shallow it barely read as flickering at all — "we have gone too far the wrong way."

- **Retuned `brokenLightFlicker`'s coefficients** for a noticeably stronger effect while staying comfortably under WCAG 2.3.1's 3-flashes/second ceiling: the fastest component is now `0.008796` rad/ms (≈1.4 Hz, confirmed by simulation at ~1.4 brightness-midline-crossings/second over a 20s run) — under half the limit, a deliberate safety margin, but roughly 4x faster than the previous ≈0.35 Hz. Brightness now swings roughly 0.23-0.92 (real-browser measurement), versus the previous attempt's 0.41-0.94 — visibly deeper dips. The continuous (non-clamping) mapping from Phase 11's follow-up fix is unchanged, so there's still no flat stretch anywhere in the cycle.
- **Verified with the same numerical + real-browser measurement approach** used throughout this flicker work: a standalone simulation for the frequency/depth claims, and a real Playwright measurement of the rendered bulb pixel (range 305 over just 2 seconds, versus 271 over 6 seconds previously; smooth 50ms-apart transitions, comfortably under the existing e2e safety test's 150-point threshold).

## Phase 14: a website-only design — dropping the Worker, and a global fallback capture

An explicit product decision: the query this site makes is simple enough, and the Worker's shared cache valuable enough mainly for the User-Agent/rate-limit etiquette it bought, that it wasn't worth keeping a server component around for. The site now calls `api.inaturalist.org` directly from the browser, and the last-resort fallback dataset was rebuilt to match.

- **`worker/` (the Cloudflare Worker adapter), `worker/wrangler.toml`, and `.github/workflows/deploy-worker.yml` are all deleted.** There is no server component left at all — no shared cache, no 7-day stale-backup, no KV namespace, no Cloudflare account needed to run this project. The `wrangler` devDependency is gone from `package.json` too.
- **`src/app.js` now constructs `InatClient` the same way the Phase 3 prototype (`live-demo.js`) always did** — no `buildUrl`/`upstreamShape: "adapter-contract"` override, just a `placeId` option, letting `InatClient`'s own default direct-to-`api.inaturalist.org` mode (`mapRawObservationToContract`/`buildQueryUrl`, already proven since Phase 3) do the fetching. This also means each poll is now a single, cheap, cursor-paginated page rather than the Worker's own full-24h-window multi-page refresh — a real simplification, not just a swap.
- **The accepted tradeoff: no custom `User-Agent`.** A browser `fetch()` can't set one (browsers silently strip it) — the entire reason Phase 4 built a server-side adapter in the first place. Every visitor's browser now also queries iNaturalist independently rather than sharing one cached refresh, so worldwide request volume scales with visitor count instead of being capped at one refresh per cache TTL. Accepted as a reasonable tradeoff for a much simpler, cache-free, server-free design; revisit if real rate-limiting shows up in practice.
- **The `#debug-status` reachability probe (`probeAdapterReachability`, distinguishing a CORS block from a DNS-level block on the Worker's own `workers.dev` subdomain) is removed** — it existed specifically to debug the Worker's own host being unreachable on some networks, which no longer applies once every request just goes to `api.inaturalist.org` itself.
- **The static fallback dataset (`src/fallback-observations.js`) was rebuilt from the busiest real 15-minute window found in a scanned 24-hour period, replacing the earlier hand-curated, research-grade-only, Colombia-only set.** Queried with the exact same scope the live feed itself uses (`taxon_id=47157`, `without_taxon_id=47224`, photos required, an appropriately-licensed photo) but with no `place_id` (global, not one country). Rather than just grabbing one arbitrary 15-minute slice, the full previous 24 hours were first scanned in 96 fifteen-minute buckets — one cheap `total_results`-only request per bucket (`created_d1`/`created_d2` bounds, `per_page=1`) — to find the densest window, then refined with a small local search around it (sliding by 5-minute steps) before fetching that exact window's observations in full: 497 real observations, captured 2026-09-15/16, 478 of which survive the family-level floor below. This maximizes how long the fallback can keep the animation populated during an outage, at a real cost — see below. Unlike the old curated set, this one is mostly `needs_id` rather than research-grade, since that's genuinely what a live feed's freshest observations look like before the community has had time to confirm them — a more honest stand-in for "the live feed, temporarily replayed" than a highlight reel of the best photos ever posted from one country. It's also less exhaustively identified than the old set: only 238 of 478 are identified to species level (the rest mostly genus-level, likely one batch of trap photos uploaded together and AI-suggested but not yet community-confirmed) — `MothStore` already renders those with its shared grey "unknown" profile, same as any live observation identified that coarsely would, so this is a realistic mix rather than a broken one, but it is a real tradeoff of optimizing for volume over identification purity.
- **Every `ObservationQueue` `app.js` constructs — the live feed's and the fallback set's alike — now runs at real, uncompressed time** (`createQueue()`'s `sourceTimeScale: 1`), overriding `observation-queue.js`'s own default ~1440x compression (tuned for the old Worker's very different full-day-window-per-poll behavior — see `DEFAULT_SOURCE_TIME_SCALE`). With Phase 14's direct client only ever returning a handful of genuinely-recent observations per poll, that heavy compression no longer made sense for the live feed either: a moth now appears roughly when it was actually posted relative to the others, which is what makes the scene read as a real live feed rather than a sped-up time-lapse. The same real-time pacing (subject to the queue's existing 0.05–3s per-item clamps) is why the fallback set — a real, time-spread 15-minute capture — plays out over a comparably long stretch instead of draining in seconds: applying the old heavy compression to a dataset already captured over just 15 real minutes would have undone the entire point of capturing that much.
- **Every observation, live or fallback, must now be identified to family level or finer.** `observation-adapter.js`'s `normalizeObservation()` — the single validation choke point both the live feed and the fallback set pass through — now rejects anything coarser (order, superfamily, and so on), using a `RANK_LEVELS` table mirroring iNaturalist's own numeric `rank_level` per rank name (confirmed against `GET /v1/taxa?rank=<name>`; family is 30, lower is finer, higher is coarser). An ID of just "Lepidoptera" (order, 40) or a superfamily grouping (33) tells a viewer nothing recognizable about the actual moth, unlike family and everything finer — exported as `isAtLeastFamilyLevel()` so other code (and tests) can check the same rule without duplicating the table. Applying this to the busiest-window fallback capture above dropped 19 of its 497 entries (3 order, 16 superfamily), leaving 478. This also supersedes the narrower fix from when that dataset was first built (`mapRawObservationToContract` blanking the generic "Butterflies and Moths" label specifically for order-rank observations) — that fix is harmless to keep, but moot for anything reaching `normalizeObservation`, since an order-rank observation is rejected outright now regardless of its label.
- **`test/e2e/site.test.js` and `species-card-observation-link.test.js` now mock `api.inaturalist.org/v2/observations` directly**, in the raw v2 response shape (`{ results: [...] }`), instead of the old Worker's already-normalized adapter-contract shape — the same pattern `live-demo.test.js` already used for the Phase 3 prototype. `test/unit/worker-adapter.test.js` is deleted along with the Worker it tested.
- **Fixed a real CI flake in the Phase 12 hover-freeze regression test**, caught on a real GitHub Actions run (`resumeDiff=1050` against a `531` threshold) that never reproduced locally. Root cause: the test assumed its own `page.waitForTimeout(60)` calls elapsed close to their nominal duration, which a slower/shared CI runner doesn't guarantee (Node timer/Playwright IPC scheduling delay under load can turn a nominal 60ms wait into something considerably longer) — more real wall-clock time genuinely elapsing after resume is correct behavior, not a jump-forward bug, but the test couldn't tell the two apart. Fixed by measuring each sampling window's *actual* elapsed time (`Date.now()`) and scaling the acceptable "normal motion" budget to that measured duration (via a motion-per-ms rate calibrated from the short baseline's own measured elapsed time) instead of assuming the nominal one — a real jump-forward bug still adds on the order of the entire ~2.8s hover's worth of motion regardless of how long the final sampling window actually took, so it stays overwhelmingly larger than this budget even with a generous safety margin.

## Phase 15: the global map concept becomes the production experience

The Robinson-projection world map explored as a standalone concept prototype (`global-map-mockup.html`) was merged directly into the production page — a visitor's first paint is now the world map behind the light, not a separate page nobody was linked to.

- **A moth's real reported location is now first-class in the shared data contract, not a mockup-only side channel.** The mockup kept a separate `locationsById` map (its own comment explained why: "this mockup-only lat/lon doesn't belong" in the shared contract) — now that the map *is* the production experience, `lat`/`lon` flow through the same pipeline every other field does: `inaturalist-client.js` requests the v2 API's `location:!t` field and parses its `"lat,lon"` string in `mapRawObservationToContract`, `observation-adapter.js`'s `normalizeObservation` validates them (null, never `0,0`, for the real minority with no location at all), and `moth-store.js` carries them onto every moth object it creates. `app.js`'s `tick()` reads `moth.lat`/`moth.lon` directly — no side-channel map to keep in sync.
- **`src/world-map.js` is the map layer**, extracted from the mockup: loading/rendering the antimeridian-aware Robinson-projection borders, drawing each active moth's steady map marker and its arrival pulse (still 5x the base fly-in duration — a quick ping, not a ring that takes as long as the flight itself), and hit-testing a pointer position against those markers. Kept independent of `app.js`'s own state, the same separation `animation-engine.js`'s `drawScene`/`projectMoth` already keep.
- **The pulse only plays on arrival, not departure**, and a moth's own opacity now fades in on the same fast, pulse-scaled timescale (`animation-engine.js`'s `opacityFadeInDuration`, also 5x faster than the base fly-in) instead of over the whole multi-second flight — previously a moth stayed nearly transparent well after its pulse had already faded away, making the arrival hard to actually see; now it reads as emerging out of the pulse, close to fully visible by the time the ring fades. A departure pulse was dropped rather than sped up to match: with the map sitting behind the light and other moths, a departure ping added visual noise without a clear moment to notice it.
- **The fallback dataset's `lat`/`lon` were backfilled** by re-querying the exact same captured window (same `created_d1`/`created_d2` bounds) with the location field added — 477 of 478 entries resolved to a real point; the one that didn't keeps `lat`/`lon: null` and falls back to the default off-canvas entry/exit, same as any live observation with no location.
- **No more per-visitor country resolution.** The site was already moving toward "the whole animation is a live global feed" (see the map's own original pitch); with the map now showing exactly where each moth was reported, scoping the query to one visitor's own country stopped making sense. `app.js` no longer imports `geolocation.js` or calls `resolveUserPlace()` — `InatClient` is constructed with `placeId: null` (never send `place_id`), and the heading/description are the static "World Moths" copy in `index.html` rather than something `app.js` used to rewrite per-country. `geolocation.js` itself is untouched and still used by the dev-only `live-demo.html` prototype.
- **Hover hit-testing checks the orbiting light show first, then falls back to a moth's map marker** (`findHoveredMothOrPoint` in `app.js`, using `world-map.js`'s `findMapPointAt`) — hovering either one focuses the same moth, and the smaller background marker never steals a hit from the light show sitting on top of it. Verified end-to-end with a real Playwright test that computes the exact same `createMapProjector()` screen position `app.js` itself would and hovers precisely there.
- **The standalone mockup (`global-map-mockup.html`, `src/global-map-mockup.js`) is deleted** — it was never linked from anywhere, and keeping it alongside the now-merged production version would just be two copies of the same thing to maintain. `src/robinson-projection.js` and `public/world-borders-110m.json` (already committed for the mockup) are unchanged and now serve the production page instead.
- **Fixed a real deploy gap found while merging this in**: `.github/workflows/pages.yml`'s "Prepare site" step never copied `public/` into the deployed `_site/` — harmless while nothing under `public/` was load-bearing, but `world-borders-110m.json` living there meant the deployed map would have silently 404'd (caught and degraded gracefully by `app.js`'s own `loadWorldBorders().catch()`, but still not what was intended). Added `cp -r public _site/public` alongside the existing copies.

## Phase 16: a live feel — greyed-out loading, upload time only, a card for every moth, and a scene that's never empty

- **Loading no longer flashes, and has no minimum.** The broken-bulb flicker (Phases 8, 11 and 13 above, kept as history) is gone — `brokenLightFlicker` and `drawScene`/`drawLight`'s `isLoading` parameter are removed, and so is the 3-second minimum display time (`MIN_LOADING_DURATION_MS`). While the first response is pending, `.canvas-shell` carries `.is-loading` (set in `index.html`, cleared by `app.js` the moment the first fetch resolves): the canvas is greyed out with a CSS `grayscale` filter and a spinner turns as a ring around the light itself (`positionLoadingSpinner` sizes and places it from the bulb's position, so it stays around the light at any screen size), caption underneath. The light stays steady throughout.
- **Why the data didn't look real-time** (measured against the live API, 2026-09-25). On first load the client used to ask for the newest 200 observations *uploaded* in the last 24 hours; that page spanned about 32 minutes (newest 30s old, median 15 min old), and the queue replays a batch from its oldest observation at real gaps, so the scene lagged the wall clock by that much and never caught up. Now `app.js` passes `initialLookbackMinutes: 2` (only the cursor-less first request uses the short window; every later request continues from `id_above` and keeps the 24h safety bound, so a delayed poll can't miss anything) and `pollIntervalSeconds: 30`. A quiet start is expected: the scene fills as uploads arrive rather than opening on a backlog.
- **Upload time is the only time.** The feed's order and pacing follow `created_at` (as they already did), and it's the only time shown — cards and pop-out both say `Uploaded 14:32` (with the date for anything not from today, e.g. the bundled fallback set), via one shared formatter, `src/observation-time.js`. The time a moth was *photographed* is ignored entirely: it's no longer requested from the API, mapped, kept by `observation-adapter.js`, or shown. (It was misleading — a median 4 hours before upload, sometimes months — and its clock-time-only display is what made entries look random and old.) Entry order itself was already strictly chronological by upload time; a replay of a real batch through `ObservationQueue` + `MothStore` had zero out-of-order admissions, and a unit test now guards it.
- **Every moth has a card.** The side panel used to skip any moth not identified to species (`activeProjectedKnownMoths` filtered on `species !== "unknown"`), so moths identified only to genus or family flew around with no card — and, via the same filter in canvas hit-testing, couldn't be hovered for a pop-out either. Both filters are gone (as is the identical one on the entry labels). A card shows the record's own name (common name, else scientific name — for a family-level record, the family) plus an `Identified to family`-style line (`formatIdentification`, from the moth's `taxonRank`), so it says exactly how precise the identification is.
- **Cards match the hover pop-out** — name, upload time, identification level, "Observed near …", photo credit — plus the "View observation" link. The panel is wider (340px) and the photo runs the full width of the card. `formatPhotoCredit` and `formatIdentification` (`animation-engine.js`) build the shared lines. The pop-out also stays clear of the open panel (`hoverState.rightInset`).
- **The pop-out no longer overflows its box.** Its box used to be sized from `max(title width, detail width, photo + text column)`, but text starts to the right of the photo, so any title or detail line wider than the 188px text column ran out past the box's right edge; titles and details were also never wrapped. Every line is now wrapped to the text column (a single over-long word is cut with an ellipsis, `wrapTextLines`) and the box is sized from that column plus the photo. An e2e test records the box edges and every drawn line from inside the page and checks each one fits, with a deliberately long name, place and credit.
- **The scene is never empty of moths.** `MothStore.holdLastMoth()` runs each tick before `removeExpired()`: a moth about to start flying out (`getExitStartTime`, exported from `animation-engine.js`, is the single definition of that instant) has its life extended unless another moth is staying beyond a small lookahead. When two are leaving together, the one with more life left is kept, so nothing already mid-fly-out is snapped back into orbit; a newly admitted moth releases the held one. `removeExpired()` additionally never removes the last moth (a backstop).
- **Real-time pacing needs real-time clamps.** `createQueue()` in `app.js` set `sourceTimeScale: 1` but left `minReleaseIntervalSeconds`/`maxReleaseIntervalSeconds` at the compressed time-lapse defaults (0.05s/3s), which squashed any real gap over 3s down to 3s — on a real sampled window, 311s of real time played back in 98s. It now passes 0.75s/30s alongside.
- **Still proposed, not done:** capping lag (skipping or speeding through a backlog older than a few minutes) and dropping the diversity thinning of the live queue to 45 (`targetSampleSize`). With a 2-minute first window the backlog is small, so neither matters much now; they would if polling stalls or uploads surge.

## Testing

```sh
npm install

npm run lint       # ESLint over src/, scripts/ and test/
npm run test:unit  # node:test against the pure animation/audio logic, no browser needed
npm run test:e2e   # Playwright: boots the real page and drives it end to end
npm test           # unit tests only (what CI's fast path runs first)
```

Unit tests (`test/unit/`) cover:
- the pure functions in `src/animation-engine.js` and `src/audio-engine.js` (orbit math, seeded randomness, color/time formatting) against a small hand-written fixture in `test/fixtures/sample-config.mjs`;
- `src/observation-adapter.js` against the real committed fixtures plus deliberately broken records (missing id, missing/invalid `createdAt`, no taxon, an incomplete photo);
- `src/species-style.js`'s determinism, bounds, and unknown-taxon fallback;
- `src/observation-queue.js`'s dedup/sort/pacing/catch-up-cap/overflow behavior (with an injected clock, no real timers) its persistence against fake and deliberately corrupt storage, and (Phase 16) that shuffled, overlapping poll batches are admitted in strict upload order and a real 20s gap isn't squashed to a few seconds;
- `src/moth-store.js`'s admit/expire/focus/capacity logic, plus one check that its output actually renders through the real `projectMoth()`, and the never-empty rule (Phase 16): `holdLastMoth()` across a long stepped run — the scene always has a moth that isn't flying out, a moth already flying out is never snapped back, and a held moth is released once a replacement arrives.
- `src/observation-time.js`'s upload-time formatting (clock time for today, the date for anything older, the year once it isn't this year, blank when unknown).
- `src/inaturalist-client.js` against a fake `fetch`/timer/clock (never the real API): mapping a raw v2 result (including the `"lat,lon"` location string — Phase 15), cursor advancement, overlap prevention, 429/`Retry-After` and jittered backoff, stale-then-recovers on a server error or network failure, the fatal-schema-error stop, offline/online handling, and adapter-contract mode.
- `src/geolocation.js` against a fake `navigator.geolocation`/`fetch` (never the real API): resolving coordinates to a standard-then-community country place, and every fallback path (unsupported, denied, timed out/unavailable, or a failed/empty `places/nearby` lookup) landing on the same United Kingdom default — still used by the dev-only `live-demo.html` prototype, though no longer by the production page (Phase 15).
- `src/fallback-observations.js` — the bundled global fallback capture (Phase 14/15): a non-trivial, genuinely species-diverse set with no duplicate ids, every entry surviving normalization with a real photo/attribution/license/observation link, a substantial number identified to species level, never anything coarser than family level, and a real lat/lon for the large majority of entries.

No DOM or browser — and no real network request — is involved in any of the above.

End-to-end tests (`test/e2e/`) spin up the zero-dependency static server in `scripts/dev-server.mjs` and drive the real pages with Playwright:
- `site.test.js` — the production page, with `api.inaturalist.org/v2/observations` intercepted (`page.route`) and answered with a canned raw-v2-shaped response (never the real iNaturalist API): launch screen → live moth rendering, the active-moths side panel populating with a real thumbnail/observation link, hovering a moth's marker on the world map focusing the same moth as its card (computing the exact same `createMapProjector()` screen position `app.js` itself would, rather than assuming one), the sound toggle, the greyed-out loading state with a spinner around a steady (non-flickering) light and no minimum display time, side-panel cards carrying upload time / identification level / place / credit with a large photo (and never the photographed time), a card for a family-level moth, every line of a pop-out with a very long name/place/credit staying inside its box, a check that nothing lands in the browser console or throws, and that the scene degrades gracefully (still renders, no thrown errors) when iNaturalist is unreachable;
- `fixtures-demo.test.js` — the Phase 2 demo: the fixture loads and moths are admitted and drawn, and the active count both stays within `maxActiveMoths` and comes back down (proving expired moths are actually removed, not just capped);
- `live-demo.test.js` — the Phase 3 demo with the real `api.inaturalist.org` request intercepted (`page.route`) and answered with a canned response: a normal poll renders moths with a `live` connection state, and a mocked 429 recovers without throwing.
- `geolocation-country.test.js` — the same page's location resolution, with `navigator.geolocation` replaced by a deterministic fake (`test/helpers/geolocation.mjs`) and `places/nearby` mocked: a granted position resolves to and displays the matching country, and a denied one falls back to and displays the United Kingdom default.
- `species-card-observation-link.test.js` — the regression case `site.test.js`'s live-moth test doesn't cover: an observation with no photo/license data hides the card's thumbnail while still showing its (always-present, real) observation link, rather than a broken image or hiding both.

Playwright needs a Chromium build. `npm ci && npx playwright install --with-deps chromium` (as CI does) downloads one; in an environment that already provides a compatible browser binary, point at it instead with `PLAYWRIGHT_CHROMIUM_PATH=/path/to/chromium npm run test:e2e` to skip the download. On a locked-down corporate Windows machine, the freshly-downloaded (unsigned, first-run) Chromium binary can get silently blocked by endpoint security — `browserType.launch: spawn UNKNOWN` with no further detail, and the browser process never even appears. The already-installed, IT-managed Edge browser (Chromium-based, so Playwright drives it identically) is a different trust profile and isn't blocked the same way: `PLAYWRIGHT_CHROMIUM_PATH="C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" npm run test:e2e`.

CI (`.github/workflows/ci.yml`) runs lint, unit tests and the Playwright suite on every push and pull request.

### Legacy offline export

`scripts/build-standalone.ps1` still generates a single, emailable HTML file from a config JSON (see `public/example-config.json` / `public/template-config.json`) for anyone who needs an offline copy. It's no longer the primary way this site is built or deployed, and its PowerShell here-string does not survive JS template literals unescaped (`` ` `` and `${...}` inside the embedded script get interpreted by PowerShell) — a known caveat to fix before relying on it again.
